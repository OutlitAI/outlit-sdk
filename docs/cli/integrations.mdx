---
title: "Integration setup (CLI)"
description: "Set up integrations and inspect their configuration readiness from the CLI."
---

The CLI exposes `outlit integrations setup`, `outlit integrations list` and
`outlit setup-sessions get`. All use the public tool gateway. For personal connections, the API key needs `integrations:connect_own`. Workspace setup needs `integrations:manage`. Outlit determines which permission applies to each provider and request.

## Integration setup

```bash
outlit integrations setup hubspot
outlit integrations setup hubspot --json
```

Setup checks the provider name locally, then calls `outlit_setup_integration` without credentials. Each call carries its own `requestId`, so a retried call returns the first answer instead of repeating the write. The CLI no longer falls back to an older browser-handoff flow.

Interactive setup can:

- Prompt for a provider credential only after the Outlit server reports the problem `credential_required`. Secret prompts
  disable terminal echo.
- Open a validated browser handoff on the configured Outlit origin. Authentication handoffs are
  polled for at most five minutes. Recovery and external setup open in the browser; the CLI does not wait for them to finish.
- Display a CRM recommendation and submit that exact mapping after confirmation.
- Display a Mixpanel preview and submit the exact mapping selected by the user.
- List a connected Stripe account's subscription metadata keys and submit the one that holds renewal
  dates. This step is optional; skipping it finishes setup as `ready`.

If setup repeats a credential, authentication, or mapping step, the CLI stops with `SETUP_STALLED`. If it cannot open a validated handoff URL, it prints the URL so you can open it yourself.

<Warning>
  Setup has no provider-secret flags. Never place provider credentials directly in command-line
  arguments, where process listings and shell history can expose them.
</Warning>

### Automation and JSON mode

Use `--config-stdin` to opt into reading exactly one strict JSON object from stdin. Its shape is
provider-specific. For example, a Fireflies API key is supplied only through stdin:

```bash
printf '%s\n' '{"credentials":{"apiKey":"<fireflies-api-key>"}}' \
  | outlit integrations setup fireflies --config-stdin --json
```

An explicit HubSpot CRM mapping is likewise supplied as the generated CRM mapping shape:

```bash
printf '%s\n' '{"configuration":{"kind":"crm_mapping","mappings":[{"pipelineId":"default","pipelineName":"Sales","mappings":[{"outlitStage":"won","crmStages":[{"id":"closedwon","name":"Closed Won"}]}]}],"confirm":true}}' \
  | outlit integrations setup hubspot --config-stdin --json
```

A Stripe renewal date field is supplied as a metadata key, or `null` to clear it:

```bash
printf '%s\n' '{"configuration":{"kind":"stripe_renewal_date_field","key":"renews_at"}}' \
  | outlit integrations setup stripe --config-stdin --json
```

In JSON mode, run setup first without `--config-stdin`: a connected Stripe account returns the step
as `step`, with each key's subscription count and a sample date (`null` when the key does not hold
dates, which makes it unusable). Then rerun with the key you chose.

The provider remains the positional CLI argument and is rejected inside the stdin document. Unknown
top-level fields are also rejected. `--config-stdin` is explicit; ordinary piped stdin is not read.

JSON mode never prompts, opens a browser, or polls. It returns the raw setup result for handoffs and
configuration previews. If credentials are required but were not supplied through `--config-stdin`,
the command exits nonzero with the problem `credential_required`. Problem codes are lowercase (`owner_required`, `credential_rejected`, and so on).

For a CRM recommendation, `--accept-recommended` submits the exact recommendation from the current
response. It conflicts with a custom CRM mapping supplied through stdin. A Mixpanel mapping must be
supplied as an exact, confirmed configuration in headless mode.

Expected provider credentials are never returned in command output. Handoff URLs must match the
configured Outlit origin, use HTTPS except for loopback development, and contain no URL credentials,
fragments, or secret-bearing query parameters.

## Integration status

```bash
outlit integrations list
outlit integrations list hubspot --json
```

`integrations list` calls `outlit_list_integrations`, one entry per provider, and returns one of five
configuration-readiness states:

| State | Meaning |
| --- | --- |
| `not_connected` | No usable provider connection exists. |
| `awaiting_auth` | Authentication must be completed. |
| `setup_required` | Provider configuration or mapping remains. |
| `ready` | Required authentication and configuration are complete. |
| `requires_intervention` | Setup needs human attention or repair. |

`ready` describes configuration readiness only. It does not promise that a sync or backfill has
finished, that customer data is present, or that provider data is current. For a connected provider
the JSON output adds a `connection` section with `lastDataReceivedAt`, `syncStatus` and
`hasSyncError`, and `setup` says whether the provider signs in with OAuth, an API key or basic auth.
The list command does not expose browser-session or raw provider-state metadata. `gmail` is accepted as a
CLI alias for `google-mail`.

## Setup sessions

A browser sign-in that setup started returns a `sessionId` in its `browser_handoff` step. Check it with:

```bash
outlit setup-sessions get <id> --json
```

The result says whether the session is `pending`, `connected`, `expired` or `failed`. It is not an
integration's ongoing status; use `outlit integrations list` for that.
