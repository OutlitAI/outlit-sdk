Integration setup and status calls use `POST /api/tools/call`. There are no public provider-credential or
disconnect REST routes. Send an Outlit bearer API key in the `Authorization` header; setup calls
for supported personal integrations use `integrations:connect_own`, while workspace or admin
setup uses `integrations:manage`. The Outlit server determines which authorization route applies to the setup
request.

## Available tools

| Tool | Purpose |
|------|---------|
| `outlit_list_integrations` | One entry per provider: its `status`, how it signs in (`setup.auth`, `setup.mode`), and a `connection` section with the last data received, sync status and sync errors. |
| `outlit_setup_integration` | Perform one bounded credential, configuration, or safe-handoff setup transition. Send `handoff: true` to start only the browser sign-in. |
| `outlit_get_setup_session` | Poll a sign-in session owned by the current actor, after a browser handoff. |

`outlit_list_integrations` replaces `outlit_get_integration_capabilities` and
`outlit_get_integration_status` (and the earlier compatibility list, which returned a different
shape under the same name). `outlit_setup_integration` with `handoff: true` replaces
`outlit_begin_integration_setup`, and `outlit_get_setup_session` replaces
`outlit_get_integration_setup_status`. Each old name keeps answering, with its old input, until the
window announced in the `outlit-notice` header closes.

The generated [OpenAPI specification](/openapi.json) and `@outlit/tools`
`publicToolContracts` contain the exact input and output schemas.

## Setup

Call `outlit_list_integrations` with the provider first when you need to know how it signs in. Do
not include credentials in this request. Then call `outlit_setup_integration` with the provider and,
when requested, its generated `connectionMode`, `credentials`, or `configuration` shape. Every setup
call takes a `requestId`: any unique string. A retry with the same id and input returns the first
result instead of repeating the setup, and a changed input needs a new id.

<RequestExample>

```bash
curl -X POST https://app.outlit.ai/api/tools/call \
  -H "Authorization: Bearer ${OUTLIT_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "tool": "outlit_list_integrations",
    "input": { "provider": "hubspot" }
  }'
```

</RequestExample>

`outlit_setup_integration` returns the provider, its canonical status, a `step` (or `null`), and a
`problem` (or `null`). `next` always names the next call. Supported steps are:

- `browser_handoff` for authentication, recovery, or provider-controlled external setup
- `crm_mapping` with the exact recommendation that can be confirmed and returned
- `mixpanel_mapping` with a preview used to choose and confirm an exact mapping
- `stripe_renewal_date_field` for a ready Stripe connection, listing the subscription metadata keys
  (`key`, `subscriptionCount`, `sampleDate`). Choose one by sending
  `configuration: { kind: "stripe_renewal_date_field", key }`, or `key: null` to clear it. The step is
  optional, and a key whose `sampleDate` is `null` does not hold dates and cannot be chosen.

On the problem `credential_required`, collect the provider's declared credential shape through a secret-safe
channel and retry once. Never log, serialize into errors, or return submitted credentials. Browser
handoffs must remain on the configured Outlit origin and must not carry credential material in the
URL. Only authentication handoffs with a session ID are polled with `outlit_get_setup_session`; recovery
and external-setup handoffs are terminal responses.

A `problem` is a state of the integration and the call itself succeeded: `owner_required`,
`connection_conflict`, `credential_required`, `credential_rejected`, `legacy_connection_required`,
`handoff_unavailable`, `sync_start_failed` or `transient_failure`, each with a `message`, `retryable`,
and sometimes a `next` call. A failure of the call itself (forbidden, invalid input, not found, rate
limited) is the error envelope. CRM stage names are lowercase (`created`, `quoting`, `negotiation`,
`won`, `lost`).

## Canonical readiness

`outlit_list_integrations` returns exactly these configuration-readiness states in `items[].status`:

| State | Meaning |
| --- | --- |
| `not_connected` | No usable provider connection exists. |
| `awaiting_auth` | Authentication must be completed. |
| `setup_required` | Provider configuration or mapping remains. |
| `ready` | Required authentication and configuration are complete. |
| `requires_intervention` | Setup needs human attention or repair. |

`ready` is not evidence that sync, backfill, or data ingestion is complete. Consumers must not
compose the setup session status, raw provider state, or the `connection` section into a different
readiness contract.
