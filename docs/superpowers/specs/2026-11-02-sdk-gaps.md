# Browser SDK gaps for marketing-site tracking (2026-11-02)

Goal: a customer (e.g. AthenaHQ) installs the Outlit browser SDK on its public marketing site and
its app, and a known contact's visit to `/pricing` lands on that contact's customer timeline.
Three gaps block that today: Safari/ITP identity loss, no bot filtering, and no documented
first-party proxy. This note records the research, my recommendations, and the split between SDK
work (this repo) and Core work (`OutlitAI/Core`, `apps/platform` ingest).

## 1. Safari ITP and visitor identity

### What the SDK does today

`packages/browser/src/storage.ts`:

- Reads `localStorage.outlit_visitor_id` **first**, then the cookie.
- Writes the cookie (`Domain=<root domain>`, 365 days) only when it mints a new id. It never
  refreshes it.

Two failures follow:

1. **Split identity across subdomains (all browsers).** `www.example.com` mints id A and stores it
   in its own localStorage. Later, `app.example.com` mints or reads id B and writes the shared
   root-domain cookie. On the next marketing visit, `www` reads localStorage A first and never sees
   B. The contact identified in the app (B) shows up on the marketing site as anonymous A. This
   lasts until `www` storage is cleared. **This is the main bug, and it is not Safari-specific.**
2. **Expiry under ITP (Safari, and every browser on iOS).** Cookies created by `document.cookie`
   and all script-writable storage (localStorage, IndexedDB, …) are deleted after 7 days without
   user interaction on the site. Script-set cookies on a landing page with link decoration (click
   ids) are capped at 24 hours. Interaction means a click, tap, or key press; scrolling does not
   count. Source: <https://webkit.org/tracking-prevention/>. Because we write the cookie only once,
   a script-set cookie dies on its original schedule even when the person visits daily.

Server-set cookies (an HTTP `Set-Cookie` header) are not subject to the script-storage rule, with
two exceptions:

- **CNAME cloaking** (Safari 14+). The response comes from a first-party subdomain whose CNAME
  points at a third party. Cookies in that response are capped at 7 days.
  <https://webkit.org/tracking-prevention/>,
  <https://webkit.org/blog/11338/cname-cloaking-and-bounce-tracking-defense/>
- **Third-party IP** (Safari 16.4+). The response comes from a server whose IP does not share the
  leading half (IPv4 /16, IPv6 /64) of the main document server's IP. Cookies in that response are
  also capped at 7 days. Snowplow:
  <https://docs.snowplow.io/docs/events/cookie-extension>. Background:
  <https://ppc.land/safari-cuts-server-set-cookies-to-7-days-on-cloaked-tracking-subdomains/>,
  <https://taggrs.io/same-origin-tracking-full-cookie-lifetime/>.

To get a full-lifetime cookie, the `Set-Cookie` must come from a response served **from the
site's own host and IP space**. A path on the site's own domain (`www.example.com/_o/...`)
qualifies when it is served by the same platform that serves the page: Next.js rewrites or
middleware, Vercel/Netlify rewrites, a Cloudflare Worker route on the same zone, or an Nginx
location on the same server. A `t.example.com` CNAME to Outlit does **not** qualify.

### What others do

- **PostHog.** posthog-js keeps its id in `localStorage+cookie` persistence. The id comes from a
  JS cookie on the root domain. PostHog's ITP answer is a reverse proxy, which mainly defeats ad
  blockers. Its managed proxy is a CNAME to PostHog/Cloudflare. That defeats blockers but is
  exactly the CNAME-cloaking case, so Safari still caps it.
  <https://posthog.com/docs/advanced/proxy>
- **Snowplow, Segment, Amplitude, server-side GTM, RudderStack.** All ship a "server-side
  cookie" or "cookie extension" endpoint served from the customer's own origin/IP. That endpoint
  re-issues the id as an HTTP cookie.
  <https://docs.snowplow.io/docs/events/cookie-extension>,
  <https://www.rudderstack.com/docs/releases/server-side-cookies/>
- **Plausible and Fathom.** They store no identifier at all, which does not fit our need.

### Recommendation (SDK, PR "a")

1. **Read the cookie first.** The root-domain cookie is the cross-subdomain source of truth.
   Order: cookie, then localStorage, then mint a new id.
2. **Reconcile.** When both exist and differ, the cookie wins and overwrites localStorage. When
   the cookie is missing but localStorage has an id (for example, ITP expired the cookie), restore
   the cookie from localStorage.
3. **Refresh on every page load.** Each time tracking is enabled, rewrite the cookie with a fresh
   expiry (365 days, as before). An active user then keeps the 7-day ITP window rolling, and app
   activity keeps the marketing-site id alive. Behind a first-party proxy, the SDK skips the rewrite
   when the cookie already holds the right id. A script write would replace the server-set
   full-lifetime cookie with a 7-day one, for example on a bounce that never flushes.
4. **Server-set cookie when a first-party proxy is in use.** If `apiHost` is same-site with the
   page, the SDK appends `?cookie_domain=<root domain it already uses>` to the ingest URL and sends
   with credentials. Core (see below) answers with
   `Set-Cookie: outlit_visitor_id=<payload visitorId>; Domain=<cookie_domain>; Path=/; Max-Age=34560000; SameSite=Lax; Secure`.
   The cookie is deliberately **not HttpOnly**, because the SDK must read it. ITP's script-storage
   cap applies to cookies *created* by script, so a server-set readable cookie keeps its full
   lifetime. The SDK sends the domain, rather than Core deriving it, so the server cookie and the
   JS cookie are the *same* cookie (same name, domain, and path). A mismatched `Domain` would create
   a duplicate cookie with the same name. Old Core ignores the query param, so the SDK change is
   safe to ship first.

**Core change (route to a Core worker).** In `app/api/i/v1/[publicKey]/events/route.ts`, after a
successful ingest, when `cookie_domain` is present:

- Validate that `cookie_domain` is a hostname suffix of the request `Origin` host.
- Validate that the Origin passed tracking-domain validation.
- Validate that `cookie_domain` is not a public suffix (`tldts`).
- Validate that `payload.visitorId` is a UUID.

Then add the `Set-Cookie` header. The browser enforces that `Domain` matches the proxy host. A
direct call to `app.outlit.ai` with a spoofed param therefore cannot plant a cookie on another
site. CORS already echoes the origin with `Allow-Credentials: true`.

**Not doing:** an HttpOnly cookie, which JS cannot read, and server-side fingerprinting.

**Open question for Core:** ids orphaned before the fix. If `www` holds localStorage id A and the
shared cookie holds B, the SDK now adopts B, and A's anonymous history stays unlinked. An optional
`previousVisitorId` on the ingest payload (a contract change) would let Core alias A to B once. I
did not build this in the SDK because it needs a Core contract change first.

## 2. Bot filtering

> **Superseded on 2026-11-02 (Leo): distinguish bots, don't block them.** AI agents and crawlers
> are now a large share of web traffic and are valuable data. Core classifies every browser event
> from its User-Agent and stores `properties.$traffic_class` (`human`, `ai_agent`, `crawler`,
> `automation`) plus `properties.$bot_name` when the UA names one. The SDK sends every event and
> adds only browser-only signals as a batch-level hint:
> `traffic: { class: "automation", signals: ["webdriver" | "headless"] }`. The `botFilter` skip
> and the SDK's UA regex were removed before release. The recommendations below are kept for
> history.

There is no filter in the SDK or in ingest today. Crawlers that execute JS (Googlebot,
Bingbot/BingPreview, AhrefsBot, GPTBot-style agents, link unfurlers, Lighthouse) and headless
automation all create anonymous visitors and pageviews.

### Research

- **PostHog** drops captures client-side for a built-in list of bot UA tokens. It also drops them
  when `navigator.webdriver` is true or the UA / `userAgentData.brands` contain `HeadlessChrome`;
  Playwright, Puppeteer, and Selenium all match. Identify and storage still work, but events never
  leave the page. <https://posthog.com/docs/product-analytics/troubleshooting>
- **isbot** (<https://github.com/omrilotan/isbot>, Unlicense) builds one regex from
  crawler-user-agents (<https://github.com/monperrus/crawler-user-agents>), Matomo
  device-detector, user-agents.net, and others. It targets self-declared "good bots", accepts
  about 1% false positives, and its full pattern is several KB. It is meant for server-side use or
  for apps that can afford the bytes.
- Malicious or stealth bots spoof real UAs. Neither layer catches them without IP reputation or
  behavioral signals, which are out of scope.

### Recommendation: both layers, with different jobs

- **SDK (PR "b"), cheap and conservative.**
  - Skip sending when `navigator.webdriver === true`, when the UA or `userAgentData.brands`
    contains `HeadlessChrome`, or when the UA matches a compact token regex:
    `bot|crawl|spider|slurp|lighthouse|headless|preview|facebookexternalhit|…`.
  - On a match, nothing is sent, so there is no network, quota, or noise cost.
  - Add an option `botFilter: false` (`data-bot-filter="false"`) for customers who run their own
    Playwright end-to-end checks against tracking.
  - Keep the regex small. The CDN script size matters, and the SDK only needs the high-volume JS
    crawlers.
- **Ingest (Core), authoritative.**
  - Run `isbot` on the request `User-Agent`. When it matches, drop the batch: return a 2xx so
    clients do not retry, and write nothing.
  - Record an aggregate `BOT_USER_AGENT` count through the existing `recordBlockedRequest`
    (grouping key = matched token), so the dropped volume is visible in Website Visitors settings.
  - This covers old SDK versions, direct Ingest API callers, and anything the compact SDK regex
    misses.
- **Drop rather than tag.** These rows would only become anonymous visitors with no business
  value, and tagging means every downstream query (timeline, visitor counts, attention) must
  remember to filter. The blocked-request counter keeps the visibility tagging would have given.
  Revisit tagging if customers ask to see crawler traffic.

## 3. First-party proxy

The SDK already supports `apiHost` (npm) and `data-api-host` (script tag). The SDK calls two
paths: `POST /api/i/v1/{key}/events` and `GET /api/i/v1/{key}/bootstrap`. Both live on
`app.outlit.ai`. The CDN script is `https://cdn.outlit.ai/outlit.js`.

### Recommended setup

- **Proxy one neutral path prefix on the site's own host.** For example, `/_o/*` maps to
  `https://app.outlit.ai/*`, and the SDK uses `apiHost: "https://www.example.com/_o"` (or
  `apiHost: "/_o"`). A path on the same host and the same platform gives:
  - immunity to ad-block lists keyed on `outlit.ai`;
  - the full-lifetime server cookie from §1;
  - no DNS or certificate work.
- Avoid names like `analytics` or `track`. PostHog's guidance is the same:
  <https://posthog.com/docs/advanced/proxy/proxy-reference.md>.
- **Copy-paste snippets for each platform:** Next.js `rewrites()`, `vercel.json`, Netlify
  `_redirects`, Cloudflare Worker, Nginx, Nuxt `routeRules`, SvelteKit hook, Astro (via its host).
  Webflow and Framer sites put a Cloudflare Worker route in front. Forward only
  `/api/i/v1/*`, never the whole Outlit app, and strip the site's `Cookie` header where the
  platform allows it.
- **One config line:** `apiHost` or `data-api-host`. Optionally serve the script itself via the
  same proxy (`/_o/outlit.js` → CDN) to also beat blockers that match the script URL.
- **Client IP caveat (needs Core).** Core runs on Vercel, and Vercel overwrites `X-Forwarded-For`
  with the connecting IP: <https://vercel.com/docs/headers/request-headers>. Behind a customer
  proxy, Core therefore sees the **proxy's** IP and `x-vercel-ip-country`. That breaks:
  - IP enrichment;
  - the consent-region bootstrap. A US-hosted proxy would mark EU visitors as not requiring
    consent. That is a compliance risk, not just a data-quality one.

  Decision: the SDK always calls **bootstrap directly on `DEFAULT_API_HOST`**, even when
  `apiHost` is set. Today `tracker.ts` sends bootstrap to `this.apiHost`, and the proxy PR changes
  that. If the direct call is blocked, it fails closed (consent required), which is safe. A
  proxied header never decides consent. The docs say "proxy events".

  Proxied events lose IP enrichment. Core's events route does no geo enrichment today, so the
  proposed `X-Outlit-Client-IP` / `X-Outlit-Client-Country` hint headers would feed nothing.
  They are **dropped** from the contract and from the snippets. Revisit if ingest gains IP
  enrichment. If it does, treat the headers as a spoofable hint, and only for enrichment.
- **Managed proxy: not now.** A managed CNAME (`t.example.com` → Outlit) defeats blockers but is
  exactly the ITP CNAME-cloaking case, so it does not fix identity. It also adds certificate and
  operations work. The path proxy is easier for most stacks and strictly better for identity.
  Revisit if many customers are on no-code hosts that cannot add a path rewrite.
